# 品牌模式 Setup 与知识库

本文档定义 **品牌关键词主体（Brand Subject）** 的设置向导流程、**品牌知识库** 能力，以及各步骤的 **操作项** 与 **数据落库** 约定。与 [01-项目说明.md](./01-项目说明.md) §6.2、[03-需求说明.md](./03-需求说明.md) FR-SUB-02 / FR-ONB、[05-诊断流程.md](./05-诊断流程.md) 01 Verify 对齐。

**文档索引**：[README.md](./README.md)

> **实现状态**：Setup 后端 API（discover / topics / prompts / finalize）与 `tb_subjects` / `tb_brands` **已实现**；**品牌模式** 的 **完善资料**（Step 1）及知识库 finalize 落库为 **【规划 P0】**，**Setup 内无知识审阅步**。域名模式仍沿用当前四步 UI。

---

## 1. 定位与目标

### 1.1 在诊断四步中的位置

品牌模式 Setup 属于 **01 Verify — 品牌信息验证** 的配置子流程：完成主体、竞品、监测主题与提示词确认，并在 finalize 建立 **verified 品牌知识库**，供后续 Dispatch / Clean / Analysis 及内容生成使用。

### 1.2 品牌模式要解决什么

| 痛点 | 知识库 + Setup 目标 |
|------|---------------------|
| 无独立官网，公开信息稀疏 | **完善资料**（用户介绍 + 文件）+ 可选 URL crawl |
| 品牌名易混淆 | 身份层：别名、否定别名、消歧说明 |
| 提示词/主题与赛道脱节 | 事实层：行业、ICP、能力、关系 |
| 推广文标题泛化、正文需准确 | 结构化主表 + 按需 RAG（非标题检索） |
| 采样提及识别不稳 | 同步 `tb_brands` 与 `subject.aliases` |

### 1.3 设计原则

| 原则 | 说明 |
|------|------|
| **Structured First** | 结构化主表为真相层（Source of Truth）；向量 chunk 为证据层 |
| **RAG On-Demand** | pgvector 从 P0 建索引能力；消费侧按场景开关，默认不检索 |
| **不用泛化标题作向量 query** | 内容生成经 Angle 映射后再 section 级检索 |
| **无图数据库** | 实体关系存 JSON / 关系字段，PostgreSQL 足够 |
| **与 `tb_brands` 分工** | 知识库重、可版本化；品牌注册表轻、服务采样解析 |
| **用户材料优先** | 品牌模式 **不调用 SearXNG**；discover 仅消费用户介绍 + 上传文件 + 可选 URL crawl |

### 1.4 品牌模式 discover 材料策略（P0）

品牌模式 **不使用 SearXNG**，**无需**也 **不提供** `SEARXNG_*` 类开关；公开网页搜索不作为品牌 Setup 的输入。

**唯一材料来源**（按优先级）：

```text
user_input（品牌介绍）> upload（文件）> homepage（品牌 URL crawl，可选）
```

**微观利基画像 / 知识抽取 / 竞品发现** 的 LLM 输入均来自上述材料（竞品发现仍可用豆包联网，与 SearXNG 无关）。

**材料不足时**（无法生成可用的微观利基画像或知识草案）：

| 项 | 约定 |
|----|------|
| HTTP | `POST …/setup/discover` 返回 **422** |
| `detail` / code | `materials_insufficient`（建议） |
| 用户文案 | 提示补充 **更完整的品牌介绍**（建议覆盖：定位、核心业务、目标客群、差异化）；可附带上传文件或填写品牌 URL |
| 前端 | **留在 Step 1 完善资料**，展示 API 返回的说明 |
| Session | **不**写入有效 `profile`；`materials_saved` 保持 true |

**「不足」判定（实现建议，满足任一即 422）**：

1. `user_corpus`（介绍 + 文件 + homepage 文本）有效字符 **< 300**（与 Step 1 校验一致，正常不应出现）  
2. 微观画像 LLM 后，关键字段仍为空或占位：如 `company` / `industry` / `customers` 等（见 `services/setup/materials.py`）  

**用户补充后**：修改介绍 / 文件 / URL → 再次 `PUT materials` → 重新 `POST discover`。

## 2. 知识库架构

### 2.1 两层存储

```text
┌─────────────────────────────────────────────────────────────┐
│  tb_subject_knowledge（结构化主表，1:1 subject）【规划 P0】   │
│  identity / facts / relations / narrative / voice / status   │
└───────────────────────────┬─────────────────────────────────┘
                            │ finalize 后投影（Setup 自动 verified）
                            ▼
┌─────────────────────────────────────────────────────────────┐
│  tb_knowledge_sources + tb_knowledge_chunks（pgvector）       │
│  来源溯源 + 分块 embedding【规划 P0 建表，P0 末/P1 按需检索】  │
└─────────────────────────────────────────────────────────────┘
                            │ sync
                            ▼
┌─────────────────────────────────────────────────────────────┐
│  tb_subjects / tb_brands（运行时兼容字段 + 提及注册表）        │
│  已实现                                                       │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 结构化主表字段（`tb_subject_knowledge`）

| JSON 字段 | 用途 | 主要消费者 |
|-----------|------|------------|
| `identity_json` | 主名、别名、否定别名、品类、消歧、**`official_url`（单值）** | finalize 落库、同步 brands；**回填 `tb_subjects.website_url` / `domain`**；采样解析 |
| `facts_json` | 行业、ICP、产品线、痛点、差异化、决策触发 | 监测主题、提示词 context、内容 Angle |
| `relations_json` | 产品↔人群、产品↔痛点等轻量关系 | 内容大纲绑 fact |
| `narrative_json` | 概述、能力 bullet 等叙事模块 | 品牌详情展示、profile_summary 渲染 |
| `voice_json` | 语气、禁用词 | 推广文 Polish |
| `sources_json` 或独立 `tb_knowledge_sources` | 溯源条目 | 品牌详情编辑、Fact-check |

| 元数据 | 说明 |
|--------|------|
| `status` | `draft` → 用户 `verified` → 变更后 `stale` |
| `version` | 每次 verify +1；文章/任务记录 `knowledge_version` |

> **物理列、索引、约束见 §2.6（已定稿）**；据此编写 Alembic migration `046_knowledge_schema`。

### 2.3 向量索引（Embedding）【规划 P0】

结构化主表存 **可审阅、可版本化的真相**；向量层存 **长文本证据**，供 P1 内容生成与 Fact-check 按需检索。**不向量化** 监测主题 / 提示词生成所需的 facts 摘要（走 Structured pack，见 §2.5）。

#### 2.3.1 索引时机

| 触发点 | 任务 | 说明 |
|--------|------|------|
| **finalize**（品牌 Setup） | Celery `knowledge.index_subject` | 自动 `verified` + 首次全量索引 |
| 品牌详情增删文件 / PATCH | `knowledge.reindex_subject` | `knowledge_version++`；Setup 外人工维护时 re-verify |
| PATCH 知识后 re-verify | INSERT 新版本 chunks | 旧 version **保留**供审计；检索仅 filter 当前 `knowledge_version` |
| `status→stale` 后 re-verify | 同上 | 与 structured 版本对齐 |

**原则**：仅对 **`status=verified`** 且 **`knowledge_version` 已知** 的快照建索引；draft 阶段不写 pgvector。

#### 2.3.2 索引流水线

```text
tb_knowledge_sources（user_input / upload / homepage）【品牌 P0；不含 searxng】
        │
        ▼ 解析纯文本（Step 1 上传已预提取；URL 在 discover crawl）
   chunker（400–600 字 / 块，overlap 50–80 字，按段落优先切分）
        │
        ▼ 批量调用 Embedding API（建议 batch ≤ 25 条/请求）
   tb_knowledge_chunks（content + embedding + source_id + knowledge_version）
        │
        ▼ P1 消费
   KnowledgeRouter.section_search(subject_id, query, top_k)
```

**纳入索引的 source kind**：

| kind | 是否分块 | 说明 |
|------|:--------:|------|
| `user_input` | ✓ | 品牌介绍全文 |
| `upload` | ✓ | 各文件独立 source，保留文件名溯源 |
| `homepage` | ✓ | crawl 正文 |
| structured `facts_json` | ✗ | 不进向量层；检索时由 Router 注入 structured pack |

> **品牌 P0** 不写入 `kind=searxng`（无 SearXNG、无配置项）。`searxng` 保留给域名模式或后续扩展，品牌模式不 populate。

#### 2.3.3 分块策略

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `chunk_size` | 500 字 | 目标区间 400–600；中文按字符计 |
| `chunk_overlap` | 64 字 | 避免句边界语义断裂 |
| 切分优先级 | 段落 → 句号 → 硬切 | 不在 URL / 英文缩写中间切断 |
| 单 source 上限 | 500 块 | 超出则截断并写 `sources_json` 告警 |
| 去重 | `content_hash`（SHA-256） | 同 subject + 同 hash 跳过重复 embed |

每块写入 `metadata_json`：`source_kind`、`file_name`（upload）、`char_start` / `char_end`、可选 `section_hint`（如「产品介绍」）。

#### 2.3.4 Embedding 模型选型

国产向量能力分两类：**云厂商托管 API**（开箱即用）与 **开源自部署**（无官方公有 API，需自建 HTTP 服务）。

| 方案 | 模型 | 接入方式 | 适用 |
|------|------|----------|------|
| **推荐 · P0** | 阿里云通义 `text-embedding-v4` | DashScope **OpenAI 兼容** `POST …/compatible-mode/v1/embeddings` | 与现有 `QIANWEN_API_KEY` 同账号；中文 RAG 成熟；可调维度 |
| 备选 API | 智谱 `embedding-3` | [open.bigmodel.cn](https://open.bigmodel.cn) REST | 维度 256–2048 可配 |
| 备选 API | 百度千帆 / 腾讯混元 / 火山方舟 | 各云 REST 或 OpenAI 兼容 | 已有对应云账号时统一账单 |
| 私有化 | BGE-M3 / bge-large-zh-v1.5 | FlagEmbedding / Xinference / TEI 自托管 | 数据不出域、调用量极大、长期降本 |

**P0 默认**：`text-embedding-v4`，**1024 维**（在 768 / 1024 / 1536 / 2048 中取质量与存储平衡）。pgvector 列维度、`embedding_model` 字段与配置 **必须一致**；换模型需 **全量 re-index**。

通义调用示例（与 OpenAI SDK 兼容）：

```http
POST https://dashscope.aliyuncs.com/compatible-mode/v1/embeddings
Authorization: Bearer $EMBEDDING_API_KEY

{
  "model": "text-embedding-v4",
  "input": ["第一段文本", "第二段文本"],
  "dimensions": 1024
}
```

#### 2.3.5 环境变量（规划）

与对话 LLM 解耦，便于日后切换 embedding 厂商：

| 变量 | 说明 | 示例 |
|------|------|------|
| `EMBEDDING_API_KEY` | API 密钥 | 可与 `QIANWEN_API_KEY` 复用 |
| `EMBEDDING_BASE_URL` | OpenAI 兼容 base | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| `EMBEDDING_MODEL` | 模型 id | `text-embedding-v4` |
| `EMBEDDING_DIMENSIONS` | 向量维度 | `1024` |
| `EMBEDDING_BATCH_SIZE` | 单次请求条数上限 | `25` |

计费：Embedding **仅按输入 token** 计费；知识库全量 index + 每次 RAG query 均消耗，量级通常 **高于单次对话**。配额 source 记 `knowledge_embed`（见 §8）。

#### 2.3.6 表结构（`tb_knowledge_chunks`）

列定义、索引与约束 **详见 §2.6.4**；本节仅保留流水线与分块约定。

#### 2.3.7 失败与重试

| 情况 | 处理 |
|------|------|
| 单批 embed API 失败 | Celery 指数退避重试；任务状态 `indexing` / `index_failed` |
| 部分 chunk 失败 | 记录 failed chunk id；整 job 标记 failed，不写入半套向量 |
| 用户 re-verify | INSERT 新版本 chunks | 旧 version **保留**；检索 `WHERE knowledge_version = :current` |
| 模型 / 维度变更 | 配置迁移 + 强制 `reindex_subject` |

### 2.4 完善资料与上传文件【规划 P0】

Step 1 **完善资料** 采集的三类输入及其在知识库中的落点：

| 输入项 | 必填 | 落点 | 用途 |
|--------|:----:|------|------|
| **品牌 URL** | 否 | `session.website_url` → finalize 写入 `identity.official_url` 并 **回填** `tb_subjects.website_url` + **`domain`（eTLD+1）**；有 URL 时另写 `tb_knowledge_sources`（`kind=homepage`） | 可选首页 crawl，补充公开信息 |
| **品牌介绍** | **是** | `session.brand_intro` → 抽取 `facts` / `narrative`；`source`（`kind=user_input`） | 用户自述为 **最高优先级** 真相来源 |
| **知识库文件** | 否 | Redis session + 对象存储（会话期）→ finalize 后 `tb_knowledge_sources`（`kind=upload`）→ chunks | RAG 证据；抽取 structured facts |

**品牌介绍** 为单一富文本字段（前端多行输入 + 写作提示），建议覆盖：

- 品牌定位
- 核心业务 / 产品与服务
- 目标客群
- 品牌优势 / 差异化

**校验**：纯文本长度 **≥ 300 字**（不计首尾空白；中英文、标点均计字符）。

**知识库文件** 约束：

| 规则 | 值 |
|------|-----|
| 允许格式 | `.docx`、`.md`、`.txt` |
| 单文件大小上限 | 5 MB（可配置） |
| 数量上限 | **10 个** / 会话 |
| 会话总大小上限 | 30 MB（可配置） |
| 解析 | 服务端提取纯文本；失败则提示重新上传 |
| 病毒扫描 | 生产环境接入扫描【规划】 |

上传文件在 **finalize 前** 存会话关联存储（对象存储或临时目录）；finalize 后迁入租户持久路径并写入 `tb_knowledge_sources`。

### 2.6 数据库表结构（Migration 定稿）

本节为 **P0 Alembic migration** 定稿，遵守 [Alembic 表规范](../.cursor/rules/alembic-table-schema.mdc)：**全列 NOT NULL**、标准三列、可选语义用哨兵值。migration revision：**`046_knowledge_schema`**（见 §2.6.6）。

#### 2.6.1 表关系

```text
tb_subjects (1) ── (0..1) tb_subject_knowledge
       │
       └── (1..n) tb_knowledge_sources
                    │
                    └── (0..n) tb_knowledge_chunks  ← embedding vector(1024)
```

| 表 | 与 subject 关系 | 职责 |
|----|-----------------|------|
| `tb_subject_knowledge` | **1:1** | 结构化真相层；status / version / index 状态 |
| `tb_knowledge_sources` | **1:n** | 溯源与原始文本（介绍、文件、URL crawl；**品牌无 SearXNG**） |
| `tb_knowledge_chunks` | **1:n**（经 source） | 分块 + 向量；**按 `knowledge_version` 快照，多 version 保留供审计** |

**不设** `tb_knowledge_uploads` 表：Setup 会话期文件走 Redis + 对象存储；finalize 后写入 `tb_knowledge_sources`。

**Migration 前置**：`CREATE EXTENSION IF NOT EXISTS vector;`（服务器已手动启用可跳过，migration 仍保留 IF NOT EXISTS）。

#### 2.6.2 `tb_subject_knowledge`

每个 **subject 至多一行**（`subject_id` 唯一，含软删过滤见索引）。

| 列 | 类型 | 默认 / 哨兵 | 说明 |
|----|------|-------------|------|
| `id` | uuid | PK | |
| `tenant_id` | uuid | FK → `tb_tenants.id` ON DELETE CASCADE | 租户隔离 |
| `subject_id` | uuid | FK → `tb_subjects.id` ON DELETE CASCADE | **1:1** 主体 |
| `status` | varchar(16) | `'draft'` | `draft` / `verified` / `stale` |
| `version` | integer | `0` | 每次用户 Verify +1；chunks 对齐此版本 |
| `index_status` | varchar(16) | `'pending'` | `pending` / `indexing` / `indexed` / `failed` / `skipped` |
| `indexed_version` | integer | `0` | 最近一次 **成功** 写入 chunks 的 version；`0`=从未索引 |
| `index_error` | text | `''` | 末次索引失败信息；成功或跳过时置空 |
| `identity_json` | jsonb | `'{}'` | 主名、别名、否定别名、品类、消歧、**`official_url`（单值字符串）** |
| `facts_json` | jsonb | `'{}'` | 行业、ICP、产品线、痛点、差异化 |
| `relations_json` | jsonb | `'{}'` | 轻量实体关系 |
| `narrative_json` | jsonb | `'{}'` | 概述、能力 bullet 等 |
| `voice_json` | jsonb | `'{}'` | 语气、禁用词 |
| `verified_at` | timestamptz | `'1970-01-01T00:00:00+00:00'` | 末次 Verify 时间；未 Verify 用 epoch |
| `verified_by_user_id` | uuid | 零 UUID | 末次 Verify 操作人；无则零 UUID |
| `created_at` | timestamptz | `now()` | 标准三列 |
| `updated_at` | timestamptz | `now()` | |
| `deleted` | boolean | `false` | |

**JSON 字段逻辑结构（非 DB 约束，供详情页编辑 / LLM 约定）**：

```json
// identity_json 示例
{
  "primary_name": "品牌名",
  "aliases": ["别名1"],
  "negative_aliases": ["易混淆名"],
  "category": "SaaS",
  "disambiguation": "非 XXX 公司",
  "official_url": "https://example.com"
}

// facts_json 示例
{
  "industry": "营销科技",
  "icp": "中小企业市场负责人",
  "products": ["产品A"],
  "pain_points": ["获客难"],
  "differentiators": ["AI 原生"]
}
```

**`official_url` 与 `tb_subjects` 回填**（品牌模式）：

| 列 | 取值规则 |
|----|----------|
| `website_url` | `validate_optional_http_url(official_url)` — 保留用户 scheme；裸 host/path 原样存；无 URL 则 `''` |
| `domain` | `registrable_from(official_url)` — eTLD+1；无法解析则 `''` |

| 时机 | 方向 | 规则 |
|------|------|------|
| Step 1 保存资料 | session | `session.website_url` 暂存用户填写的品牌 URL |
| finalize | session → **`tb_subjects`** + knowledge | `identity.official_url` ← `session.website_url`（规范化）；按上表回填 `website_url`、`domain` |
| Setup 外 PATCH + re-verify | knowledge → subject | `official_url` 变更后同步更新两列 |

`identity_json.official_url` 为 **真相来源**；`tb_subjects.website_url` / `domain` 为运行时兼容字段（引用率、采样、展示等已有逻辑），二者应与 knowledge 保持一致。

**无官网的品牌**：`official_url`、`website_url`、`domain` 均为 `''`（与当前「品牌主体 domain 可为空」一致，但有 URL 时必须双写）。

**域名模式**（对照）：仍由 Step 0 网站 URL 决定 `domain` + `website_url`，**不**走 `identity_json.official_url`。

实现复用 `services/subject/domain_fields.py` 中 `parse_url`、`registrable_from`（与域名主体归一逻辑同源）。

**索引与约束**：

| 名称 | 类型 | 列 | 说明 |
|------|------|-----|------|
| `uq_subject_knowledge_subject` | UNIQUE | `subject_id` | `WHERE deleted = false` |
| `ix_subject_knowledge_tenant` | B-tree | `tenant_id` | |
| `ix_subject_knowledge_status` | B-tree | `subject_id`, `status` | `WHERE deleted = false` |

#### 2.6.3 `tb_knowledge_sources`

| 列 | 类型 | 默认 / 哨兵 | 说明 |
|----|------|-------------|------|
| `id` | uuid | PK | |

**kind 与 Setup 落点**（摘要；**字段级说明见 §2.6.3.1**）：

| kind | 典型 title | raw_text 来源 | 条数 |
|------|------------|---------------|------|
| `user_input` | `品牌介绍` | Step 1 `brand_intro` | 通常 1 |
| `upload` | 原始文件名 | 文件解析文本 | 每文件 1，≤10 |
| `homepage` | 页面 title 或 URL | homepage crawl | 0 或 1 |

#### 2.6.3.1 三种 `kind` 存什么（品牌 P0）

四种 `kind` 均在 `tb_knowledge_sources` 占 **一行**（品牌 P0 仅用前三种），存 **原始证据文本**（`raw_text`）与溯源；finalize 后按 `raw_text` 分块写入 `tb_knowledge_chunks`。

**优先级**（LLM 抽取与冲突裁决）：`user_input` > `upload` > `homepage`。

```text
Step 1 用户输入
├── brand_intro ──► user_input（1 条 raw_text）
├── 上传文件 ─────► upload（N 条 raw_text + storage_key）
└── 品牌 URL ─────► homepage（0~1 条 crawl raw_text）

discover 自动（无 SearXNG）
         │
         ▼ 微观画像 + 竞品发现
         ▼ 材料不足 → 422，留 Step 1 补介绍
         ▼ finalize：持久化 sources + 自动 verified + index → tb_knowledge_chunks
```

##### `user_input` — 品牌介绍

| 项 | 说明 |
|----|------|
| **触发** | Step 1 完善资料，用户必填「品牌介绍」（≥300 字） |
| **条数** | 通常 **1 条** / subject |
| **`title`** | 固定如 `品牌介绍` |
| **`uri`** | `''` |
| **`raw_text`** | 用户介绍的 **完整正文**（定位、业务、客群、优势等） |
| **`mime_type` / `file_size` / `storage_key`** | 空 / 0 / `''`（非文件） |
| **`metadata_json`** | 可选：session id、保存时间 |
| **还去哪** | discover 并入 `user_corpus`（**最高优先级**）；finalize 写入 sources 并分块向量化 |
| **不存** | 未填写内容；介绍以外字段不在此行生成 |

##### `upload` — 知识库上传文件

| 项 | 说明 |
|----|------|
| **触发** | Step 1 上传 `.docx/.md/.txt`（可选，≤10 个） |
| **条数** | **每个文件 1 条** |
| **`title`** | 原始文件名（如 `产品介绍.docx`） |
| **`uri`** | `''` 或内部存储路径 |
| **`mime_type`** | 如 `text/plain`、`application/vnd…wordprocessingml.document` |
| **`file_size`** | 文件字节数 |
| **`storage_key`** | 对象存储 key；**二进制在 OSS**，不在 DB |
| **`raw_text`** | 服务端 **解析出的纯文本** |
| **`parse_status` / `parse_error`** | 解析成败与原因 |
| **`metadata_json`** | `upload_file_id`、扩展名、上传批次等 |
| **还去哪** | 会话期二进制在 Redis + 临时/OSS；**finalize 后**写入本表并分块（chunk 带 `file_name`） |
| **不存** | docx 等二进制进 `raw_text` |

##### `homepage` — 品牌官网 crawl

| 项 | 说明 |
|----|------|
| **触发** | Step 1 填写品牌 URL 后，discover 对首页/落地页 crawl |
| **条数** | **0 或 1 条**（未填 URL 则不创建） |
| **`title`** | 页面 `<title>`，或退化为 URL |
| **`uri`** | 用户填写的品牌 URL（规范化） |
| **`raw_text`** | crawl 得到的 **正文纯文本**（去 HTML） |
| **`mime_type` / `file_size` / `storage_key`** | 空 / 0 / `''` |
| **`metadata_json`** | crawl 时间、HTTP 状态、最终跳转 URL 等 |

| **不存** | 完整 HTML、图片、样式 |

#### 2.6.4 `tb_knowledge_chunks`

**仅 embedding 成功后 INSERT**（不写入半套向量）；`embedding` 列始终有值。

| 列 | 类型 | 默认 / 哨兵 | 说明 |
|----|------|-------------|------|
| `id` | uuid | PK | |
| `tenant_id` | uuid | FK → `tb_tenants.id` ON DELETE CASCADE | |
| `subject_id` | uuid | FK → `tb_subjects.id` ON DELETE CASCADE | 检索必过滤 |
| `source_id` | uuid | FK → `tb_knowledge_sources.id` ON DELETE CASCADE | 溯源；孤立块用零 UUID（不应出现） |
| `knowledge_version` | integer | `0` | 与 `tb_subject_knowledge.version` 对齐 |
| `chunk_index` | integer | `0` | 同一 source 内序号，从 0 起 |
| `content_text` | text | `''` | 块正文（400–600 字目标） |
| `content_hash` | varchar(64) | `''` | SHA-256 hex；同 version 去重 |
| `char_start` | integer | `0` | 在 source.raw_text 中起始偏移 |
| `char_end` | integer | `0` | 结束偏移（不含） |
| `token_count` | integer | `0` | 估算 token；计费核对 |
| `embedding` | **vector(1024)** | — | pgvector；维度随 `EMBEDDING_DIMENSIONS` |
| `embedding_model` | varchar(64) | `''` | 如 `text-embedding-v4` |
| `metadata_json` | jsonb | `'{}'` | `source_kind`、`file_name`、`section_hint` 等 |
| `created_at` | timestamptz | `now()` | 标准三列 |
| `updated_at` | timestamptz | `now()` | |
| `deleted` | boolean | `false` | 仅 **来源删除** 时置 true；re-index **不**因 version 变更软删旧 chunks |

**索引与约束**：

| 名称 | 类型 | 列 | 说明 |
|------|------|-----|------|
| `uq_knowledge_chunks_source_idx_ver` | UNIQUE | `source_id`, `knowledge_version`, `chunk_index` | `WHERE deleted = false` |
| `ix_knowledge_chunks_subject_ver` | B-tree | `subject_id`, `knowledge_version` | `WHERE deleted = false` |
| `ix_knowledge_chunks_hash` | B-tree | `subject_id`, `content_hash`, `knowledge_version` | 去重辅助 |
| `ix_knowledge_chunks_embedding_hnsw` | **HNSW** | `embedding` **`vector_cosine_ops`** | 近似检索；P0 建索引 |

**检索 SQL 约定**（P1 Router）：

```sql
SELECT id, content_text, source_id,
       embedding <=> :query_embedding AS distance
FROM tb_knowledge_chunks
WHERE subject_id = :subject_id
  AND knowledge_version = :version
  AND deleted = false
ORDER BY embedding <=> :query_embedding
LIMIT :top_k;
```

#### 2.6.5 哨兵值与状态机

| 哨兵 | 用于 |
|------|------|
| 零 UUID | `verified_by_user_id` 未设置 |
| `''` | 可选字符串未设置 |
| `0` | 数值未用 / version 初值 |
| `1970-01-01T00:00:00+00:00` | 尚未 Verify |

**status × index_status 协作**：

| status | index_status 典型流转 |
|--------|-------------------------|
| `draft` | `skipped` 或 `pending`；不写 chunks |
| `verified` | `pending` → `indexing` → `indexed`（或 `failed`） |
| `stale` | 保持末次 `indexed_version`；re-verify 后 version++ 再 index（旧 version chunks **保留**） |

## 3. Setup 流程总览

### 3.1 品牌模式 UI 步骤（目标态）

品牌模式在 **品牌设置** 与 **竞品/主题/提示词** 之间仅插入 **完善资料**；**discover**（微观画像 + 竞品发现）在 **完善资料提交后** 自动触发，不单独占一步。**Setup 内不设知识审阅**——用户自述即真相；知识库在 **finalize** 时自动落库并索引。

```text
Step 0 品牌设置 → Step 1 完善资料 → [discover 自动] → Step 2 选择竞品
    → Step 3 审查主题 → Step 4 确认提示词 → finalize（知识库 + 向量索引）
```

| UI Step | 名称 | 已实现 | 说明 |
|---------|------|:------:|------|
| 0 | 品牌设置 | ✓ | 仅品牌名、区域、语言；**创建 session** |
| 1 | **完善资料** | ✗ | **【P0】** URL、品牌介绍（≥300 字）、知识库文件（≤10） |
| — | *智能发现* | 部分 | 离开 Step 1 后自动：`discover`（loading） |
| 2 | 选择竞品 | ✓ | 展示 discover 产出的竞品列表 |
| 3 | 审查主题 | ✓ | 读 session `profile` / 规划读 structured pack |
| 4 | 确认提示词 | ✓ | 同左 |
| 5 | 完成落库 | ✓ | finalize + 知识库持久化 + **自动** 向量索引 |

**域名模式**（对照）：无 Step 1；Step 0 填 **网站 URL** 后直接 `discover` → 竞品 → 主题 → 提示词 → finalize（共 **4 步 UI**）。

|------|------|
| 1 | 校验竞品（品牌主体：竞品 brand 必填） |
| 2 | 竞品 hash 变化则重跑 **问句扩词 + 主题聚类**（`run_topic_generation_stage`） |
| 3 | 规则 QA（`topic_qa.validate_topic_clusters`） |
| 4 | 生成/刷新 **profile_summary** Markdown LLM |

**AI 配额**：问句扩词、主题聚类、`profile_summary` 各计一次（竞品未变且 session 已有 `topic_clusters` 则跳过主题 LLM）。

**LLM 输入**：`niche_profile`（含 `topic_lexicon`、`features`）+ 已确认竞品场景摘要 + 候选问句（聚类阶段）。

**数据保存**

| 存储 | 字段 | 内容 |
|------|------|------|
| Session | `competitors` | enrich 后完整竞品 |
| | `confirmed_competitors_hash` | 竞品集合 hash |
| | `monitoring_topics` | `string[]`，5 条主题名 |
| | `topic_clusters` | 含 `name`、`decision_dimension`、`seed_queries` |
| | `candidate_queries` | 扩词阶段候选问句 |
| | `profile_summary` | Markdown 全文 |
| | `prompts_hash` / `prompts_cache` | 竞品或主题变则清空 |
| 前端 | `topicRows` | `{name, selected, decisionDimension}`；Step 3 只展示决策维度标签 |

---

### Step 4 — 确认提示词

**用户操作**

- 按主题查看生成的监测问句（禁品牌名）
- 增删改；可重新生成（`exclude_prompts`）
- 确认 → `finalize`

**后端操作（`POST .../setup/prompts`）**

| 序号 | 操作 |
|------|------|
| 1 | 读取 session `topic_clusters`，按选中 themes 调用 `SETUP_WIZARD_PROMPTS_SYSTEM` |
| 2 | 优先基于各 topic 的 **seed_queries** 扩展；每条带 `funnel_stage`、`search_intent` |
| 3 | Session 缓存 `prompts_cache`（同 hash 复用） |

**AI 配额**：`source=setup`，按主题批量生成。

**Context（当前）**：session `profile` + entity/competitors 等。  
**Context（规划）**：`identity` + `facts` + competitors；**不启用 RAG**。

**数据保存**

| 存储 | 字段 | 内容 |
|------|------|------|
| Session | `prompts_cache` | 按 topic 分组的 prompts |
| | `prompts_hash` | 生成参数 hash |
| 前端 | `promptRows` | 扁平列表含 topic 名 |

---

### Step 5 — 完成落库（finalize）

**用户操作**

- 确认后提交；跳转主体 Dashboard；触发首次采样

**后端操作（`POST .../setup/finalize`）**

| 序号 | 操作 |
|------|------|
| 1 | 配额：主体数、提示词总数、每品牌平台数 |
| 2 | 创建 `Subject`；`apply_competitors` |
| 3 | `sync_subject_brands_from_setup` → `tb_brands` |
| 4 | 创建 `Topic`（`name` + `decision_dimension`）、`Prompt` |
| 5 | `create_and_enqueue_sampling_job` |
| 6 | 【规划】写入 `tb_subject_knowledge`（`status=verified`，`version=1`）；迁移 session 资料 → `tb_knowledge_sources`；`identity.official_url` ← `session.website_url` |
| 7 | Celery `knowledge.index_subject`：sources → 分块 → embedding |
| 8 | 双写 `niche_profile`、`summary`；**`tb_subjects` ← `official_url`**：`website_url` + `domain`（eTLD+1，见 §2.6.2） |
| 9 | 删除 setup session 及临时上传文件 |

**数据保存（PostgreSQL — 已实现）**

| 表 | 主要字段 |
|----|----------|
| `tb_subjects` | `type=brand`，`brand`，**`domain`（← eTLD+1）**，`aliases`，**`website_url`（← `official_url`）**，`profile_summary`，`summary`，`niche_profile`，`sampling_frequency` |
| `tb_competitors` | 竞品 domain/brand/website/summary/aliases… |
| `tb_brands` | own + competitor 品牌注册行 |
| `tb_topics` | 主题名 |
| `tb_prompts` | 问句 text、funnel、intent、topic_id |
| `tb_sampling_jobs` | 首次采样任务 |

**数据保存（规划 P0）**

| 表 | 说明 |
|----|------|
| `tb_subject_knowledge` | verified JSON + version |
| `tb_knowledge_sources` | user_input / upload / homepage |
| `tb_knowledge_chunks` | embedding；含 upload 与介绍拆分块 |

**Session**：删除。

## 5. 品牌模式 vs 域名模式差异

| 项 | 品牌模式 | 域名模式 |
|----|----------|----------|
| Step 0 输入 | 品牌名、区域、语言 | 网站 URL → 主域 |
| Step 1 完善资料 | **有**（URL / 介绍 / 文件） | **无**（URL 已在 Step 0） |
| Setup 内知识审阅 | **无**（用户自述即真相；finalize 自动落库） | **无** |
| discover 触发时机 | 完善资料提交后 | Step 0 下一步 |
| 主信息来源 | **用户介绍 + 上传文件** > URL | 首页 crawl > SEO |
| `tb_subjects.domain` | ← `registrable_from(official_url)`；无 URL 则 `''` | eTLD+1（Step 0 网站） |
| `tb_subjects.website_url` | ← `official_url`（finalize 回填） | Step 0 网站 URL |
| 竞品 brand | **必填** | 可仅 domain |
| 引用率指标 | 依赖登记 URL | 主域引用 |
