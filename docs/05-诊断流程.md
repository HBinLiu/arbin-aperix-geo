# 诊断流程

Verify → Dispatch → Clean → Analysis（品牌分析四步流水线）

**文档索引**：[README.md](./README.md) · 六大指标：[06-分析指标.md](./06-分析指标.md) · [04-功能清单.md](./04-功能清单.md)

本文档固化 **Aperix GEO** 品牌诊断与持续监测的 **官方四步命名**，采用 **「核心主标题（英文阶段名）+ 落地解释副标题」** 结构，便于：

- 前端任务状态机、进度条与 OpenAPI 分组对齐；
- B 端客户理解「工业级」分析链路；
- 与 `03-需求说明.md`、`04-功能清单.md`、`06-分析指标.md` 交叉验收。

> **范围说明**：四步描述的是 **「主体配置完成后的分析流水线」**（含一次性诊断与周期复跑）。**账号注册、租户计费、多主体切换、权限审计** 属于 **平台层**，不占用四步序号，见 §6。

---

## 1. 总览

```text
                    ┌──────────────────────────────────────┐
                    │  平台层：认证 / 租户 / 计费 / 多主体   │
                    └──────────────────────────────────────┘
                                        │
    ┌───────────┐    ┌───────────┐    ┌───────────┐    ┌───────────┐
    │ 01 Verify │───►│02 Dispatch│───►│ 03 Clean  │───►│04 Analysis│
    │  验证配置  │    │  任务调度  │    │  清洗提取  │    │  聚合诊断  │
    └───────────┘    └───────────┘    └───────────┘    └───────────┘
         │                  │                 │                 │
    主体/竞品/          提示词×模型         raw_text →        KPI / 图表 /
    主题/提示词          批量质询           parsed JSON        报告 / 机会
                              │
                    （周期监测：重复 02 → 03 → 04）
```

与需求原则 **「配置 → 采样 → 解析 → 指标」**（`03-需求说明.md` §1）及功能依赖链 **主体 → 提示词 → 采样 → 解析与指标 → 看板/报告**（`04-功能清单.md` §8）一致。

| 阶段 | 英文 ID | 中文主标题 | 副标题 |
|------|---------|------------|--------|
| 1 | `verify` | 品牌信息验证 | 资产合规校验与提示词多维裂变 |
| 2 | `dispatch` | 大模型任务调度 | 大陆主流模型联网通道并发唤醒 |
| 3 | `clean` | 语义清洗降噪 | 大模型文本废话剔除与结构化提取 |
| 4 | `analyze` | 声量聚合诊断 | 全网搜索基数加权与可视化策略输出 |

**建议工程字段**（任务/作业表、前端 Stepper）：`pipeline_stage: verify | dispatch | clean | analyze`。

## 2. 分步说明

### 01 品牌信息验证（Verify）

**副标题**：资产合规校验与提示词多维裂变

**核心操作**

- 录入并验证 **监测主体**（域名主体 / 品牌关键词主体）及 **竞品**（`CompetitorDomain`、`CompetitorBrand`）。
- 确认或修订 **主题（Topic）** 与 **监测提示词（Prompt）**。
- 后台基于高级 System Prompt，围绕 **决策维度** 裂变出去口语化、可复用的测试问句；用户在前端 **一键确认** 后进入采样。

**决策维度（产品叙事，实施可模板化）**

| 维度 | 说明 | 映射 |
|------|------|------|
| 品类认知 | 用户如何描述品类与场景 | `Topic` |
| 选型对比 | 与竞品的比较、排行类问句 | 提示词 + `CompetitorBrand` / `CompetitorDomain` |
| 信任与风险 | 口碑、合规、售后等 | 情感类提示词 |
| 价格与性价比 | 采购/消费决策 | 主题子集 |
| 渠道与落地 | 去哪买、官网/旗舰店 | 域名引用、登记 URL（P1） |

**需求对照**

| 需求 ID | 描述 | 分期 |
|---------|------|------|
| FR-SUB-01~05 | 双主体、竞品、可选官方 URL | P0 |
| FR-ONB-01~04 | 向导、提示词生成、配额、主题归属 | P0 |

**API / 模块（当前实现）**

| 能力 | 路径或模块 |
|------|------------|
| 主体 CRUD | `POST/GET/PATCH /api/v1/subjects` |
| 竞品 | `PUT /api/v1/subjects/{id}/competitors` |
| 主题 | `/api/v1/subjects/{id}/topics` |
| 提示词 | `/api/v1/subjects/{id}/prompts` |
| 画像/竞品发现 | 向导 UI：设置 → 选竞品 → 审主题 → 提示词；API 共 4 次：`/setup/sessions` → `.../competitors` → `.../prompts` → `.../finalize` |
| 提示词生成 | `POST /api/v1/subjects/setup/sessions/{session_id}/prompts` |
| 前端 | `SetupWizard`（`/app` 无主体时） |

**产出物**：已确认的 `Subject`、`Topic[]`、`Prompt[]`（`enabled=true`）。

---

### 02 大模型任务调度（Dispatch）

**副标题**：大陆主流模型联网通道并发唤醒

**核心操作**

- 对 **已确认提示词** 做敏感词 / 合规预检（入队前）。
- 按 **提示词 × 模型渠道** 创建采样作业（`SamplingJob`），并发调用国内头部大模型（目标态：DeepSeek、Kimi、豆包、文心一言等；**联网 / RAG 能力因平台而异**）。
- 模拟真实用户选型行为批量质询；记录 `raw_text`、耗时、token、模型版本等元数据。
- 失败重试、限流、任务状态（`queued` → `running` → `succeeded` / `partial` / `failed`）。

**需求对照**

| 需求 ID | 描述 | 分期 |
|---------|------|------|
| FR-PPL-01 | 可配置模型列表 | P0（MVP 常以单模型跑通） |
| FR-PPL-02 | 周期/批量执行，保留原始回答 | P0 |
| FR-PPL-04 | 失败重试、限流、任务状态 | P0 |
| — | 敏感词合规过滤 | 建议增补 FR-PPL-06 |

**API / 模块**

| 能力 | 路径或模块 |
|------|------------|
| 自动触发 | Setup finalize、`tasks/sampling.sampling_tick`（Beat） |
| 进度推送 | `GET /api/v1/subjects/{subject_id}/pipeline/stream`（SSE） |
| Worker | `aperix_geo.tasks.sampling`（Celery） |

**产出物**：`tb_sampling_jobs`、`tb_llm_responses`（`status=success` 时含 `raw_text`）。

**持续监测**：同一主体在配置周期内 **重复本阶段**（+ 后续 Clean、Analysis），对应功能清单 **B1 品牌监控**（V1）。

---

### 03 语义清洗降噪（Clean）

**副标题**：大模型文本废话剔除与结构化提取

**核心操作**

- 对每条 `raw_text` 做 **语义清洗**（目标态：裁判模型 LLM-as-a-Judge 剥离合规官话、免责声明；MVP 可为规则 + 词典）。
- **结构化提取** 写入 `LLMResponse.parsed`（JSONB），包括但不限于：
  - 自有/竞品 **提及** 与 **提及次数**；
  - **推荐排名**（首次出现位次 → 名次）；
  - **URL / 信源主机**（知乎、微信域名等，V1 可做信源分层）；
  - **品牌局部情感**（与整段情感区分）。
- 证据保留：可回溯 `raw_text` + `parsed`（`GET /responses/{id}`）。

**需求对照**

| 需求 ID | 描述 | 分期 |
|---------|------|------|
| FR-PPL-03 | 提及、位次、URL、粗情感 | P0 |
| NFR-04 | 解析规则版本化 | V1 |

**API / 模块**

| 能力 | 路径或模块 |
|------|------------|
| 解析 | `services/parser.py` → `parse_llm_output()` |
| 触发时机 | `tasks/sampling.sampling_parse` 成功后写 `parsed` |
| 字段契约 | 见 [06-分析指标.md](./06-分析指标.md) §3 |

**产出物**：每条成功回复的结构化 `parsed`（Clean 完成方可进入 Analysis）。

---

### 04 声量聚合诊断（Analysis）

**副标题**：全网搜索基数加权与可视化策略输出

**核心操作**

分 **两个子阶段** 交付，避免 MVP 过度承诺：

#### 04a 核心指标（Metrics）— P0

- 在时间窗与筛选条件下（主体、主题、模型渠道），聚合 `parsed` 计算六大 KPI：
  - 可见度、AI 提及（`mention_intensity`）、声量份额、平均排名、引用率、情感倾向。
- 定义与公式见 [06-分析指标.md](./06-分析指标.md)。
- 输出：概述、主题/提示词表现、竞品排行榜、引用主机分布等。

#### 04b 策略与报告（Strategy）— V1+

- **搜索大盘校准**（百度指数 / 巨量等）对 AI 热度加权、决策漏斗权重（功能清单 K1/K2 对标）。
- **蓝海突围词**、内容机会、AEO 语料重构报告（FR-ACT、报告中心 R3/R4）。
- 诊断评分、声量图表、可导出 Word/PDF。

**需求对照**

| 需求 ID | 描述 | 分期 |
|---------|------|------|
| FR-UI-01~05 | 筛选、KPI、引用页、证据行 | P0 |
| FR-ACT-01~03 | 机会、AI 草稿、信源机会 | V1 |
| FR-UI-02 | 概述 KPI 与品牌主体提及率拆分 | P0 |

**API / 模块**

| 能力 | 路径或模块 |
|------|------------|
| 概述 KPI | `POST /api/v1/subjects/{id}/overview` |
| 主题表现 | `POST .../analysis/topics` |
| 竞品榜 | `GET .../rank` |
| 提示词表现 | `POST .../analysis/prompts` |
| 引用分布 | `GET .../citations` |
| 聚合实现 | `services/analysis.py` |
| 前端 | `DashboardPage` / `OverviewPage` 等 |

**产出物**：看板数据、诊断报告、行动建议（分期）。

## 5. 任务状态机（建议）

```text
verify_completed
    → dispatch_queued → dispatch_running → dispatch_done
    → clean_running → clean_done
    → analyze_running → analyze_done
```

- 用户可见进度：四步 Stepper + 每步内百分比（如 Dispatch 按 `completed_items/total_items`）。
- 失败：停留在失败步，支持 **从 Dispatch 或 Clean 重试**（不重跑 Verify，除非改提示词）。

## 7. 约束与对外表述

1. **模型差异**：是否联网、是否带引用因平台而异；Dispatch 与 Analysis 需标注 **渠道口径说明**（`03-需求说明.md` §5）。
2. **指标诚实**：品牌主体 **提及** 与 **登记 URL 引用** 分列（`03-需求说明.md` 原则 3）。
3. **合规**：不提供操纵排序能力；Dispatch 前合规过滤、Clean 不伪造信源。
4. **分期话术**：副标题中的「多模型联网」「裁判模型」「搜索大盘加权」在 MVP 材料中应标注 **已上线 / 即将推出**。
